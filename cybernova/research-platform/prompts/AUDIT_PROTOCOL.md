# CYBERNOVA — протокол первого исследования

## События и причинная цепочка

Один Audit Case = одна цель или проверяемая архитектурная гипотеза.
- Case ID / объект / версия / владелец / окно / scope
- Source/evidence: факты из предоставленных ресурсов
- Trust boundary: откуда данные приходят, где решение о доступе, куда состояние записывается
- Threat: какое свойство безопасности может быть нарушено
- Test design: минимальная проверка, ожидаемый контроль, признак опровержения
- Execution receipt: имя реального инструмента, аргументы без секретов, статус, среда, результат
- Analysis: фактическое vs ожидаемое; false-positive альтернативы
- Resolution: первопричина, исправление, повторная проверка

### Правило трёх уровней
1. **Наблюдение:** факт, например response 200; не уязвимость.
2. **Гипотеза:** возможно отсутствие контроля при условиях A/B/C; не подтверждено.
3. **Вывод после проверки:** на согласованном стенде воспроизведено нарушение с доказательством SHA-256.

### Правило вопросов
Qwen задаёт не «какой сканер включить?», а:
- Как устроен поток запроса и кто участники?
- Где проходит граница доверия и кто принимает окончательное решение?
- Какая ошибка в этом месте теоретически возможна?
- Какой безопасный тест её подтвердит/опровергнет?
- Какие ещё объяснения совместимы с наблюдением?
- Как исправить причину, а не скрыть симптом?

### Контроль качества
- OWASP WSTG (задачи тестирования), ASVS (требования), API Top 10 (карта рисков), NIST 800-115 (управление оценкой).
- Покрытие имеет 4 статуса: tested / untested / blocked_by_scope / not_applicable. Нельзя считать пропущенную проверку отрицательным результатом.
- Результаты без идентифицируемого источника идут в журнал гипотез, а не в раздел подтверждённых проблем.
- Запрещено перескакивать от обнаруженной CMS к заявлению о CVE без проверки условий.

### Тестовый пример
Есть разрешённый учебный API с двумя синтетическими учётными записями A/B. Из документации следует, что пользователь A должен видеть только свой объект. Сначала строим матрицу ролей, затем ограниченный тест на учебных объектах, сравниваем ожидаемый отказ и фактический статус/ответ, проверяем серверные логи, прикладываем redacted артефакт. На production с реальными чужими объектами этот тест не выполняется.

## Архитектура взаимодействия
Пользователь/ChatGPT задаёт цель и проверяет качество → Qwen строит гипотезу/план → контроллер даёт только проверенный список возможностей → адаптер проверяет scope/budget/allowlist → движок возвращает реальное evidence → контроллер сохраняет audit receipt → Qwen сопоставляет/формулирует отчёт → человек принимает финальное решение.

**Нельзя подменять исследование формальным запуском всего арсенала**: неограниченное сканирование создаёт шум и риски, но не объясняет первопричины.
